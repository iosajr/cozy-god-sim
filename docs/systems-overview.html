Deferred

The one decision everything else follows from

Simulation state is plain data owned by a single store. The scene tree is a view of that data, generated for whatever's on screen and thrown away when it isn't.

This is one decision answering two problems at once. Debuggability, because there's a single place where the truth lives — state stops being scattered across thirty spawned bodies you have to go find. And scale, because a node costs the engine something every frame just by existing, while a record costs nothing until someone reads it.

A node is a puppet. It knows which record it's showing and nothing else — no simulation state is ever stored on it, so destroying one loses nothing.

The systems

Numbered by dependency: each one can be built with only the ones above it existing. Every system gets its own document when it gets built — this page stays a map.

01

Clock

One absolute game time, and the rate it runs at.

  • A single number that only ever goes up: in-game seconds since the world began. Everything that happens is stamped with it.
  • Time of day, day number, season and year are all read off that number, never stored next to it. Nothing can disagree with itself.
  • Seasons are first-class: crops, weather and behaviour vary by them, rather than having a calendar retrofitted once farming needs one.
  • Speed is one multiplier. Paused, normal and fast are the same code path, not three.
  • Systems are handed elapsed seconds and advance by them. Nothing counts frames.
Not its jobIt doesn't know what a day means to a villager. It reports the time; anything that cares about the time asks.
02

World

Owns every simulated record. The one place to look.

  • Plain data — entities, settlements, buildings, tasks, events. No scene-tree types anywhere inside it.
  • Stable ids. Anything that refers to an entity holds its id, never the object, so nothing breaks when an entity is removed.
  • One tick entry point. The world advances its systems in a known order; nothing advances itself from its own frame callback.
  • It runs headless. If the world needs a window open to be correct, something's in the wrong place.
Not its jobNo rendering, no input, no camera. It doesn't know it's being watched.
03

Entities & Species

Every living thing, sharing one shape.

  • A species is an authored resource, not a subclass. Lifespan, speed, diet, gestation, size, what it looks like, and which behaviours it's allowed. Adding a goat is filling in fields in the editor.
  • One Entity class underneath all of them: id, position, species, born at, personality, memories, current task.
  • Subclass only for a genuine difference in kind — something that builds versus something that can't, something rooted versus something that walks. Never for different numbers.
  • Behaviours are a small named set a species is granted. A sheep gets graze, wander, flee. A villager gets work, eat, sleep, socialise, build. The behaviour code is shared; the grant list is per species.
  • Nothing stores age. It stores when it was born, and age is the clock minus that.
Not its jobA species describes capability and constants. It holds no logic — the behaviours do, and they're shared across everything granted them.
04

Memory

Everything an entity knows, and when it learned it.

  • One class covers everything an entity knows — something that happened to it, and somewhere it knows about. The shape is the same either way: what, where, when, how much it mattered, who else was there.
  • Kinds are flags on that class, not separate types. Witnessing something divine is a memory with a flag set, sharing everything else.
  • Memories are what an entity acts on. Nothing ever asks the world for the nearest food — it goes to the place it remembers, which may be gone. Cheaper than a spatial search, and wrong in ways that read as character rather than as bugs.
  • Strength is computed from age when read, never ticked down. An entity nobody watched for a year reads exactly the same as one watched the whole time.
  • Capped per entity — keep the strongest handful, drop the rest. Uncapped memory is the thing that quietly eats the game later.
  • Spreads only when entities actually meet. An event pushes to whoever was there; nothing ever scans everyone against everyone.
  • Personality is a fixed base plus the pull of whichever memories are currently strong, computed the same way.
  • The list doubles as the entity's readable history — the debuggability you asked for and the memories you asked for are the same feature seen from two sides.
Not its jobIt records what an entity knows. It doesn't choose what the entity does — desires read it, it doesn't drive.
05

Settlement & Jobs

The village as a real thing, and the coordinator that hands out work.

  • A Settlement owns its members, its stores of food and material, and its buildings. Its shortages are what create available work.
  • Anything with a semi-fixed location and a community is one — a village, a warren, a grove. A single class, with each species naming its own.
  • The job manager is its own module, not part of the settlement. It holds the universal jobs every entity does regardless of where it lives — eat, sleep — and takes village-specific information as input.
  • Entities still hold their own references. A villager knows its own home; a house knows its own occupants. The settlement isn't the only thing that knows where anything is.
  • Coordination lives here precisely so entities don't negotiate with each other. Anything needing two entities to agree goes through the settlement rather than between them.
Not its jobThe settlement publishes what's needed. It never decides who does it — entities choose for themselves.
06

Tasks & Desires

What an entity decides to do, and doing it.

  • A task is a whole job — sleep, eat, harvest that field — never a single action. Sleep is find shelter, go there, rest. Eat is get food, go home, eat.
  • Steps are shared between tasks. "Go to a place" and "wait a while" are written once and reused by everything that needs them, rather than each task reimplementing its own travel.
  • Needs are derived, never ticked. An entity stores when it last ate and last slept; hunger and tiredness are computed from how long ago that was. Nothing depletes, nothing needs a periodic check, and an entity untouched for an hour is correct the moment anyone reads it.
  • The strongest need, weighted by that entity's own interests, chooses what happens next — so the same job scores differently depending on who is asking.
  • An entity picks its target from what it remembers, not from the world. It walks to the field it knows of — which may not be the nearest, and may not still be there.
  • Task is a real base class with one subclass per kind. Claim it, run it, finish or abandon it. No parallel bookkeeping files reimplementing the same shape per job type.
  • Legibility is a requirement, not a bonus. Watching one villager for thirty seconds should tell you what it wants and why.
Not its jobTasks move and change entities. They draw nothing.
07

View, Camera & Terrain

Turning records into something on screen.

  • One spawner for everything. It asks what's near the camera and creates or destroys visuals for those records. A sheep becomes visible exactly the way a villager does, because its species says what it looks like.
  • Camera is drag-the-world, zoom toward a point, rotate around focus — hands on the landscape rather than keys on a vehicle.
  • Terrain sits behind one interface: height at a point, and whether it can be walked. Flat is an implementation of that interface, not an assumption.
  • Pluggable only works if nothing assumes flat. Movement and placement ask the terrain for a height starting now, while the answer is always zero — that's what makes the swap real later instead of aspirational.
Not its jobThis layer reads the world. It never writes to it.
08

Checks

Catching the game contradicting itself, while it runs.

  • Named checks over the world: a task claimed by nobody, memories over the cap, an entity off the map, starving but idle. Run on a cadence, report what fires.
  • They run against the live game, which is where the real bugs were — not against a mock in a separate process.
  • One inspector panel over the store, styled like Godot's own so it reads as familiar. It lists whatever is currently in view, and opening a row shows every field, the memories with timestamps, the current task and what was just finished.
  • Because it reads the store, it works for records with nothing spawned. Something off-screen can still be inspected — being drawn is never a prerequisite for being readable.
  • Every bug found by hand becomes a check, so the same one can't come back quietly.
Not its jobChecks observe and report. They never repair, and never change what the game does.

Two habits that pay for everything later

Neither costs anything now. Both are painful to retrofit, and between them they're what keeps the door open to real scale without designing for it today.

Advance by elapsed time, never by frame

Anything that accumulates is written as advance(state, elapsed) from its first line. Written this way, catching something up after an hour untouched is one call. Written as "do a bit each frame", it can never be caught up at all without rewriting it.

Never store what the clock can tell you

Age, memory strength, how long since something last ate — store the timestamp, compute the answer on read. Nothing to tick, nothing to go stale, and something nobody has looked at for a year is automatically correct.

Deferred on purpose

Not forgotten, and not designed around either. Each of these has one thing keeping its door open, and nothing more spent on it than that.

Pokémon-styled terrain
The interface exists from day one and flat sits behind it. When you approve a real terrain, it swaps in and nothing else in the game notices.
Massive scale
With one settlement, machinery for simulating distant places is dead code. The two habits above are the whole preparation, and they're free.
Gods acting on the world
Needs a world worth acting on first. Entities, tasks and memory have to be running before an intervention means anything.
The LLM helper
Reads memories and events, writes nothing, blocks nothing. The game must run identically with it switched off, so it can be added whenever.

How the documents work now

Same discipline as the code.

  • One document per system, written when that system is built. No document tries to describe the whole game.
  • Documents say what is true now. No history, no superseded versions, no pointers to other files.
  • One list of things awaiting your decision, raised regularly. Anything that doesn't get decided gets deleted rather than left sitting.
  • Few rules, stated plainly, and anything not covered gets asked about rather than assumed.

Build order

Straight down the dependency chain, with the first lookable thing as early as it can honestly come.

  1. Clock and World. Nothing else can be written honestly without them, and they're small.
  2. Entities, species, the view spawner and the camera. The first thing worth looking at: flat ground, a handful of villagers and sheep standing on it.
  3. Memory, then settlement and jobs. Entities know about places; the settlement has shortages and publishes work.
  4. Tasks and desires. The first thing worth watching — villagers wanting things and going to get them.
  5. Personality and event memories. The same structure, now carrying what happened as well as where things are.
  6. Checks and the inspector, growing from step one onward rather than waiting for a phase of their own.

Black & White here means the 2001 Lionhead game, the reference for camera feel and villager behaviour — separate from Pokémon as the reference for terrain styling. The memory-and-desire structure and the village-as-coordinator both come from how that game actually worked, not from guesswork. Everything else on this page comes from what you've said directly.
